# 04: An outbox event whose type can't be resolved fails clearly and is retried

**What to build:** When the transactional outbox reads a pending event whose stored type name matches no loaded type, the failure names the event type and the event, and the lookup isn't remembered, so a later attempt can still succeed. Today `IntegrationEventLogService.ResolveEventType` (`src/IntegrationEventLogEF/Services/IntegrationEventLogService.cs:20`) caches the result with `GetOrAdd` even when it is `null`, for the whole process. The `null` then reaches `JsonSerializer.Deserialize(Content, null)` and throws a generic `ArgumentNullException` while the pending events are enumerated. In Ordering that happens in `TransactionBehavior` after the business change has been committed, so the request fails even though its data was saved.

**Blocked by:** None (can start immediately)

**Status:** done

- [ ] Only successful lookups are cached; a failed lookup is tried again next time
- [ ] An unresolvable type is reported with an error that names the stored type name and the event id, not an `ArgumentNullException` from the serializer
- [ ] Tested against a real database: a pending entry with an unknown type name is marked Failed with that error logged, and the transaction's other pending entries are still published
- [ ] One unresolvable event is marked Failed and skipped; the other pending events in the same transaction are still published (decided in triage, 2026-11-18)

## Comments

- Introduced deliberately in test-strategy ticket 02. That change moved the lookup off `Assembly.GetEntryAssembly()`, the test host under `WebApplicationFactory`, onto all loaded assemblies, and added the cache. It's unlikely in practice, because events are written and read in the same process, so their type is loaded. That's why this was left as a follow-up.
- Not observable through the seam: that a failed lookup is retried and not cached. Showing it would mean loading an assembly at runtime in a test. Check it in review instead.
- Triage, 2026-11-18: confirmed from the code. Besides the generic error, the cached `null` poisons that type name for every later event in the process, and because the deserializing is lazy it throws inside the publishing loop but outside its per-event `try`, so the events after the bad one are never published (nothing republishes `NotPublished` events). Decision: mark the bad event Failed and skip it, as the loop already does for a publish failure.

## Agent Brief

> *This was generated by AI during triage.*

**Category:** bug
**Summary:** An outbox event whose stored type name resolves to no loaded type is logged with its type name and id, marked Failed and skipped, and the lookup is not cached.

**Current behavior:**
`IntegrationEventLogService.RetrieveEventLogsPendingToPublishAsync` resolves each entry's `EventTypeName` through a process-wide cache that also stores failed (`null`) lookups. A `null` type reaches `IntegrationEventLogEntry.DeserializeJsonContent`, which throws a generic `ArgumentNullException` from `JsonSerializer`. The throw happens while Ordering's `OrderingIntegrationEventService.PublishEventsThroughEventBusAsync` enumerates the pending entries, outside its per-event error handling, so the request fails after the business change was committed and the remaining events of that transaction are never published.

**Desired behavior:**
- Only successful type lookups are cached; a failed lookup is attempted again the next time that type name is seen.
- When an entry's type can't be resolved, the error logged names the stored type name and the event id.
- That entry is marked `PublishedFailed`; every other pending entry of the same transaction is still published and marked `Published`.
- The request that triggered publishing does not fail because of it.

**Key interfaces:**
- `IIntegrationEventLogService` / `IntegrationEventLogService<TContext>`: the type resolution and `RetrieveEventLogsPendingToPublishAsync`. Its contract may change (e.g. how an unresolvable entry is reported), as long as Ordering's caller is updated with it.
- `OrderingIntegrationEventService.PublishEventsThroughEventBusAsync`: an unresolvable entry goes through the same "log, mark Failed, continue" path as a publish failure.
- `EventStateEnum.PublishedFailed`: the existing state for a failed event; no new state.

**Acceptance criteria:**
- [ ] With two pending entries in one transaction, one with an unknown type name and one valid, publishing marks the unknown one `PublishedFailed` and the valid one `Published` (states read back from a real Postgres database), and only the valid event reaches the event bus.
- [ ] The logged error for the unknown entry contains its stored type name and its event id.
- [ ] A failed lookup isn't cached (checked in review; not observable through the seam, see the comment above).
- [ ] Existing Ordering and Catalog tests still pass.

**Seams (CLAUDE.md, Testing):** the outbox query and state updates against the real database, through the Ordering functional tests' Postgres; `IEventBus` is a boundary we don't own, so a fake or NSubstitute there only.

**Out of scope:**
- A background sweeper that republishes `NotPublished` or `PublishedFailed` events.
- Changing how events are serialized or how type names are stored.
- Catalog's own publishing path, which doesn't read pending entries back.
